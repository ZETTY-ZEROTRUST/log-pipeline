# $zetty-integration-test

사용자가 지정한 ZETTY 로컬 통합 테스트를 실행합니다. 테스트 케이스·선택자·이미지 태그는 각각 의미가 다르므로 요청과 실제 runner 옵션에서 확인합니다. 임의의 branch→tag 규칙을 만들지 않습니다.

## 이 파일의 역할 — 오케스트레이션만

**시나리오 정의는 이 파일에 두지 않습니다.** 실행 절차·검증 명령·기대 응답은 전부
`attack-simulation/README.md`, `log-pipeline/pipeline/README.md`, `zero-trust-architecture/compose/README.md`의 실제 실행 절차가 소유하며, 이 command는 "어떤 케이스를 고르고,
어떤 순서로 태우고, 어떻게 보고할지"만 규정합니다.

시나리오·기대값은 실제 owner 문서와 테스트 코드에서 읽습니다. endpoint·payload·예상 결과를 이 스킬에 복제하지 않습니다. Markdown 케이스 문서가 없어도 기존 테스트 함수·runner가 검증 범위와 기대값을 정의할 수 있습니다.

경로는 ZETTY 워크스페이스 기준입니다. 개별 레포 clone에서는 현재 레포의 README와 테스트 코드를 먼저 읽고, 없는 형제 레포가 필요한 검증만 미실행으로 보고합니다.

## 실행 순서

### Step 0 — 테스트 케이스 선택

사용자가 지정한 케이스·명령·실패 결과가 있으면 그것을 선택합니다. 없으면 대상 변경과 owner README에서 해당 테스트를 찾습니다.

- backend: 변경 앱의 현재 테스트. PostgreSQL 전환을 실제로 구현하는 요청일 때만 별도 PostgreSQL 검증 절차를 추가.
- log-pipeline: `pipeline/tests/integration/run.sh`와 실제 pytest 테스트·선택자.
- attack-simulation: `README.md`의 현재 네 시나리오와 앞으로 구현될 실제 runner. 삭제된 `scenarios/v2/`·`load/`를 실행 경로로 안내하지 않는다. 정의만 있고 runner가 없으면 실행 미구현으로 보고한다.
- Compose: `compose/README.md`의 구성·기동·복구 검증.

서로 다른 실행 대상 중 선택이 필요한 경우에만 사용 가능한 질문 도구 또는 일반 질문으로 필요한 범위를 확인합니다. 이미 지정된 케이스를 재확인하지 않습니다.

### Step 1 — 시나리오 범위 선택

요청의 전체/일부 범위와 실제 테스트 의존 관계를 확인합니다. 실행 가능한 선행 setup이 명확하고 승인된 범위에 포함되면 함께 실행하고 알립니다. 의존 관계가 불명확하다는 이유로 일부 요청을 전체 실행으로 넓히지 않습니다. 해결할 수 없는 의존 부분만 질문 또는 SKIP으로 남깁니다.

local target allowlist·모의 계정·요청량·기간·timeout·종료 조건을 실제 runner와 맞춥니다. 선택 완료 후 케이스·대상·예상 정리 범위를 한 줄로 알립니다.

### Step 2 — Setup 실행

실제 owner의 전제 조건과 명령을 읽고, 승인된 로컬 테스트에 필요한 의존성·이미지·일회용 서비스를 준비합니다. 명령을 다른 레포에서 실행하거나 기존 stack을 테스트용으로 초기화하지 않습니다. 이미지 태그는 명시된 override 또는 실제 runner의 규칙만 사용합니다.

현재 DB는 MySQL입니다. PostgreSQL은 향후 전환 방향이며 이 스킬 설치로 전환됐다고 보고하지 않습니다. 향후 전환 구현 범위에서 PostgreSQL schema 초기화를 할 때는 새 테스트 DB에만 적용합니다. 기존 DB의 데이터 이동·스키마 전환은 해당 검증 절차를 따르며 초기화 SQL을 무조건 재실행하지 않습니다.

### Step 3 — 시나리오 실행

Step 1에서 확정한 시나리오를 케이스 파일의 정의대로 실행합니다. 각 시나리오의 PASS/FAIL은
**케이스 파일이 명시한 기대값**으로만 판정합니다(이 command가 기대 코드를 따로 정하지 않습니다).

### Step 4 — Teardown

runner의 cleanup/trap 또는 케이스의 Teardown을 확인해 자신이 만든 일회용 컨테이너·네트워크·임시 파일만 정리합니다. 기존 서비스의 기동 상태와 데이터 볼륨은 유지합니다.

### Step 5 — 결과 보고

케이스 파일에 `보고 양식`이 있으면 그 양식을 그대로 씁니다. 없으면 아래 기본 양식을 사용합니다.

```
[run-integration-test] 완료

## 케이스
<케이스 제목> (<파일 경로>)

## 이미지
<해당 앱의 로컬 검증 이미지>

## 결과 요약
| 번호 | 테스트 | 결과 | HTTP |
|------|--------|------|------|
| ...  | ...    | ...  | ...  |
(실제 실행한 시나리오만 행으로 넣습니다 — 스킵된 것은 결과란에 SKIP과 사유)

PASS: N · FAIL: N · SKIP: N

## FAIL 상세 (있을 때만)
- <번호>: <테스트명> — 기대 <기대값>, 실제 <실제값>
  응답: <바디 요약>

## 비고
- 컨테이너: <이름> (종료·삭제 여부)
- 임시 파일: 정리 여부
```

FAIL이 있으면 `docker logs <컨테이너>`의 관련 구간에서 비밀·토큰·쿠키·업무 본문을 제거한 진단을 첨부하고, 아래 블록을 생성합니다:

```
## 수정 요청 ← 이 블록을 $zetty-fix-test-failure 에 그대로 전달

케이스: <케이스 파일 경로>
실패 시나리오:
- <번호>: <테스트명> — 기대 <기대값>, 실제 <실제값>
  응답: <바디 요약>
  컨테이너 로그: <관련 ERROR 줄>

이미지: <해당 앱의 로컬 검증 이미지>
브랜치: <현재 브랜치>
```

## 중단 조건

- owner 문서와 실제 코드에서 검증 정의를 찾을 수 없음 → 해당 검증 미실행과 필요한 정의를 보고.
- 승인된 준비로 해결할 수 없는 전제 조건 미충족 → 해당 범위만 SKIP, 가능한 독립 검증 계속.
- 기동 timeout → 해당 서비스 진단을 민감값 제거 후 보고하고 자신이 만든 자원 정리.
- 선행 시나리오 실패 → 실제 의존 규칙에 따라 후속만 SKIP. 독립 케이스는 계속.
- 수정 요청이 있으면 설치된 `$zetty-fix-test-failure`를 적용. 스킬이 없으면 같은 원인 분석→제한된 수정/검토→실패 케이스 재검증 절차를 주 세션에서 수행하고 독립 검토 여부를 보고.
## ZETTY 실행 제한
요청에 케이스·범위가 명시되면 다시 묻지 않는다. 불명확할 때만 필요한 범위를 확인한다. local allowlist·모의 계정·요청 수·기간·종료 조건을 확인한다. 자신이 만든 일회용 자원만 정리한다. JWT/쿠키/비밀번호/키/업무 본문은 실패 보고에서 제거한다.

## 현재 구현과 구성의 범위
현재 ZETTY DB 구현은 MySQL이며 PostgreSQL은 향후 전환 방향이다. 스킬·에이전트 구성만 요청된 작업에서는 실행 코드·SQL·Compose·의존성·데이터를 변경하지 않는다. 위 절차의 구현·실행 단계는 해당 작업이 실제 요청된 경우에만 적용한다. 경로는 ZETTY 워크스페이스 기준이며 개별 clone에서는 자기 레포의 README와 실제 코드를 먼저 읽고 없는 형제 레포의 교차 검증만 미실행으로 남긴다.
